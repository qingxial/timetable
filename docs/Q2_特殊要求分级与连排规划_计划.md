# Q2 计划：分级满足特殊要求 + 学时/日连排时段划分

> 目标：当课程有特殊要求时，以特殊要求为准灵活排（4/7/8 节连排、跨天 3+4 等）；
> 多条要求并存时按 **任课老师 > 课程类别级/学院级 > 全校级** 取舍，只落地最高级那条。

---

## 0. 现状盘点（据实）

- **引擎已能连排 >2 节**：`tryloadlimit.new_generate_day_patterns` 的 `preferred_groups` 分支
  在 `:274` 直接 `return`，绕过了末尾 `all(h<=2)` 的 ≤2 过滤器（`:360`）。绑定组 `[…]`
  内块长不限，唯一硬条件是**组内总学时 = 周学时**（`:265`）。
- **入口缺口**：默认（无绑定组）分支强制"每天≤2节"；`specialneeds.py`（LLM 版）会把 PKYQMS
  翻成 `Prefer_Time`，但**不区分级别、不生成多块连排、不做优先级取舍**。
- **数据现实**：本期 465 条 PKYQMS = 学院级 361 / 班级级 36 / 周次限制 68，**全是 2 节窗口、
  无任课老师级、无 >2 连排、每门至多一条**。故 Q2 是"补能力 + 造样例验证"，非现有失败驱动。

结论：**核心算法基本不用改**，主要补三层——① 要求分级模型；② 优先级解析器；
③ 学时→日连排时段的块划分器（并给 `new_generate_day_patterns` 开一个 `max_block` 口子）。

## 1. 分级满足特殊要求

### 1.1 要求数据模型 `RequirementSpec`
```
level          : 3=任课老师 / 2=课程类别·学院 / 1=全校        # 数字越大越优先
kind           : 'placement'(指定时段/连排) | 'week'(仅单双周/仅周末) | 'forbid'(禁排)
scope_key      : 具体归属（教师号 / 学院名 / 类别名 / '全校'）
allowed_days   : set[int] 或 None（不限天）
block_template : list[int] 连排块，如 [4] / [3,4] / [2,2]；None=用默认块划分
fixed_periods  : list[[a,b]] 明确节次窗口（可空）
source_text    : 原始 PKYQMS 片段（留痕）
```

### 1.2 级别判定（从数据推断，不新增列）
- 文本前缀 `学院：…` → level 2（scope=学院）；`班级:…` → level 2（scope=班级，同"类别级"）；
- `仅单周 / 仅周六周日` → level 1（全校/课程级周次限制，kind='week'）；
- 校历硬禁排（周二 5-8、unavailable_Time）→ level 1，kind='forbid'；
- **任课老师级（level 3）**：本期无数据。预留两条入口——
  (a) PKYQMS 出现 `老师/教师：X` 或显式连排要求（`4节连排`/`周一1-4节`）；
  (b) 未来教师维度的独立要求表。解析后 scope=教师号。

### 1.3 优先级取舍（核心规则）
对每个教学班 JXBID，收集所有命中的 RequirementSpec，按下述规则合成一条"生效要求"：

1. **禁排是"减法"、永远生效**：所有 level 的 `forbid`（校历禁排 + unavailable）取并集，
   作为不可占用区，**任何更高级要求也不能排进禁排区**（安全底线，不被覆盖）。
2. **定位是"加法"、最高级独占**：`placement`/`week` 类里，
   `level` 最大的那条胜出；同级多条冲突 → 记为冲突并取最先出现的一条（并在松弛记录里标注被丢弃项）。
3. 生效要求 = { 胜出的 placement/week } ∩ { 全体 forbid 的补集 }。
   若胜出要求与禁排冲突到无解 → 该要求判为不可行，降级为软偏好（进 Q3 松弛记录），不硬塞。

> 落地形态：把"生效要求"翻译成 `Prefer_Time` 的**绑定组 `[…]`** 字符串写回课程表，
> 复用引擎既有的 `preferred_groups` 通路——**算法层零改动即可支持多块连排**。

## 2. 学时划分 + 日连排时段（块划分器）

输入：整数总学时 `T = LLXS`（理论学时，锚点）、生效要求（allowed_days / block_template / max_block）。
输出：若干 `(days_list, hours_list)` 候选模式，供 `new_check_period_availability` 试排。

### 2.1 块模板 → 日分配
- **要求已给显式模板**（如 3+4）：`block_template=[3,4]`，`sum` 必须 = T，直接用；
  按 allowed_days 里枚举有序的 `len(template)` 个不同天，一天一块。
- **要求给"整块 K 节连排"**（如 4 节连排）：`max_block=K`，用带余划分把 T 拆成块：
  `q, r = divmod(T, K)` → q 个 K 块 +（r>0 时）1 个 r 块；块数 = 每天一块 → 需要的天数。
  例 T=8,K=4 → [4,4]（2 天）；T=7,K=4 → [4,3]（2 天）；T=6,K=4 → [4,2]。
- **无特殊块要求**：走现有默认（≤2 块）规则，行为不变。

### 2.2 给 `new_generate_day_patterns` 开口子
新增两个可选参：`max_block=2`（默认，保持旧行为）、`block_template=None`。
- 末尾过滤器由 `all(h<=2)` 改为 `all(h<=max_block)`；
- 有 `block_template` 时直接按模板枚举天组合，跳过 ZXS 分支；
- 默认调用（不传参）**完全不变**——对现有 4400+ 门零影响。

### 2.3 天分配约束
- 每块落在不同 allowed_day；块间可留间隔（沿用现有"隔 2-3 天"倾向，非强制）；
- 落位后仍走全部硬约束（教师/班级/教室/禁排/校历）；
- 与小数拆分（@FA/@FB 周次分段）**正交**：多块连排作用于"天×节次"，小数分段作用于"周次"，
  两者独立叠加，字段互不覆盖。
